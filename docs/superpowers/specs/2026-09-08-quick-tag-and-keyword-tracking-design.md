# 快速標籤鍵 + 關鍵字建檔追蹤

**日期**：2026-09-08
**模組**：`app_unified/`（notes 藍圖、標籤系統、新增追蹤模組）
**Repo**：`webapp`
**相關**：`2026-07-03-attachment-thumbnails-design.md`（標籤系統的既有設計脈絡）

## 動機

兩個獨立需求，都來自每天的實際操作痛點。

### 需求一：交接時逐項掛標籤太慢

admin 與 super_admin 每天交接，會在 checklist 上一項一項核對，核對完掛一個標籤
表示「super_admin 已知曉」。目前掛標籤要開項目 modal、進標籤選擇器、勾選、儲存 ——
一項就是好幾次點擊，一次交接二十幾項就變成純粹的體力活。

使用者要的是：**項目旁邊直接一顆按鈕，按下去就掛上並顯示。**

附帶一個硬性條件：**不可以改變項目的排序**。使用者已經被勾選那條路徑咬過 ——
`update_checklist_item` 裡 `if changed: item.updated_at = now`，而項目列表預設按
`updated_at DESC` 排序，所以勾選會讓項目在下次載入時跳到最上面。新按鈕不能重蹈覆轍。

### 需求二：關鍵字散落在各處，追不動

某個員工的名字（或任何需要持續追蹤的事）會出現在不同日期、不同筆記的 checklist
項目裡。目前只能每次重新搜尋一遍，搜完就散了、沒有累積，也沒辦法記錄「這一筆我
已經處理過了」。

使用者要的是：**把某個關鍵字的所有命中集合成一張表，持續累積、可以標記狀態。**

## 命名

新功能叫 **「建檔追蹤」**。

命名本身是設計的一部分：這個功能與現有的關鍵字搜尋**會打架**——兩者都是輸入關鍵字、
都會列出命中結果，使用者很容易搞混。所以流程刻意分成兩段：

- **搜尋**：現有行為，即時、暫時性，關掉就沒了。
- **建檔追蹤**：在搜尋結果頁按下「建檔追蹤」，才會真的建立一張持續累積的表。

曾考慮「列管」（台灣行政語境的標準用語，語意最精準）與「關注清單」（語氣較輕），
最後選「建檔追蹤」——最白話、不會被誤解成搜尋，也不帶「列管」那種對人的負面暗示。

## 需求一設計：快速標籤鍵

### 哪些標籤會變成按鈕

**沿用現有的「釘選」機制**，不新增設定項目。

`Tag.pinned` 目前的語意是排序（每店最多 3 個，釘選的排在標籤管理與選擇器前面，
`notes/tags.py:53`、`PIN_LIMIT = 3`）。本設計**擴充**它的語意：釘選的標籤同時
在編輯器上渲染成一鍵按鈕。

已評估並否決的替代方案：另加一個獨立的 `quick` 欄位，讓「釘選」與「快速鍵」分開。
彈性較高，但要多一個欄位 + migration + 管理介面多一個控制項，而使用者確認不需要
「釘選但不做按鈕」這種組合。

實務上店家會建一個叫「陳店長知道」的標籤並釘選，按鈕上就顯示那個名字 —— 使用者
說的「顯示 xxx 知道」就是靠標籤名稱本身達成，不需要程式去組字串。

### 按下去發生什麼

- 已釘選的標籤在**每個 checklist 項目旁**與**筆記的標籤區**各渲染一顆按鈕。
- 按一下掛上；再按一下取消（誤按可還原）。
- 掛上時記錄**誰按的、什麼時候**；滑鼠移上去顯示「王小明 9/08 08:15」。
- **不觸碰 `updated_at`** → 排序不變。這是硬性條件，需有測試守著。

### 資料模型

`note_tags` 與 `checklist_item_tags` 各新增三欄：

| 欄位 | 型別 | 說明 |
|---|---|---|
| `tagged_by` | FK users, `ondelete="SET NULL"` | 誰掛的 |
| `tagged_by_name` | `EncryptedText` | 帳號快照，比照 `ChecklistItem.checked_by_name` 的既有模式（刪帳號後仍查得到） |
| `tagged_at` | DateTime | 什麼時候掛的 |

三欄皆 nullable —— 既有資料沒有這些值，UI 遇到 null 就不顯示 hover 資訊。

需要 migration。兩張表目前都是複合主鍵，加 nullable 欄位是安全操作。

### 必須一併修正的既有缺陷

`notes/tags.py` 的 `set_note_tags`（:166）與 `set_item_tags`（:195）目前是
**「先全刪再重插」**：

```python
ChecklistItemTag.query.filter_by(item_id=item.id).delete()
for tid in tag_ids:
    db.session.add(ChecklistItemTag(item_id=item.id, tag_id=tid))
```

只要使用者之後從標籤選擇器動過任何一個標籤，剛存下的 `tagged_by` / `tagged_at`
就會被整批洗掉。**必須改成差集操作**：只刪除被移除的、只插入新增的、原有的不動。

這個缺陷在加欄位之前是無害的（純關聯表，刪了重建沒差），加欄位之後會變成靜默資料
遺失，所以是本功能的前置條件而非「順手改進」。

### 邊界情況

- `MAX_TAGS_PER_ITEM = 5`。已滿時按快速鍵要回**明確的錯誤訊息**，不可靜默無反應。
- 權限沿用現有標籤指派：同店即可（`notes/tags.py` 的 `note.store != current_user.store`
  檢查）。不新增權限概念 —— 按的人是 user/admin，顯示的名字來自標籤本身。

## 需求二設計：建檔追蹤

### 流程

1. 使用者用現有的關鍵字搜尋找「王小明」。
2. 搜尋結果頁出現「建檔追蹤」按鈕。**不按 = 現有行為，關掉就沒了。**
3. 按下去 → 建立一張追蹤表，並跑第一次完整比對（會慢，僅此一次）。
4. 之後每次開這張表，只比對**上次掃過之後才出現的資料**（增量）。

### 這張表長什麼樣

**入口**：筆記首頁（`/notes/`）的功能區新增一個「建檔追蹤」連結，進去是同店所有
追蹤表的清單；點一張進到 `/notes/tracking/<id>`，標題形如「王小明 建檔追蹤」。
**不**混進筆記列表，避免把日報洗版。

**建檔的入口**：搜尋結果頁（`/notes/?q=王小明`）在結果上方顯示「建檔追蹤」按鈕；
若該關鍵字在本店已有追蹤表，改顯示「開啟追蹤表」。

每一列是一筆命中：

```
┌────────────────────────────────────────────┐
│ 備註：9/08 已口頭告誡，觀察一週             │  ← 備註在最上面
│ 9/08  B店日報 · 項目                        │
│ 王小明遲到 10 分鐘                          │
│                          [不相關]  [→ 原文] │
└────────────────────────────────────────────┘
```

- **備註在每一列的最上面**（使用者指定）——因為追蹤的重點是「我對這件事做了什麼」，
  那比原始文字更需要第一眼看到。
- **[→ 原文]** 連回原始的筆記／項目。
- **[不相關]** 把這一列剔除，之後不再出現。整店共用（一個人剔除，大家都不再看到）。

### 參照，不是複本

每一列存的是**指向原始資料的參照**，不是複製一份文字。

已評估並否決：複製成真正的 `Note` + `ChecklistItem`。那樣可以直接沿用所有既有功能
（勾選、附件、提醒），但**原始項目被修改或刪除後，追蹤表不會跟著變** —— 會出現
「追蹤表寫著遲到 10 分鐘、原始項目已更正成 5 分鐘」的落差，對一個要當作依據的表
來說是致命的。

取而代之：參照 + 每一列自己的狀態（備註、是否剔除）。內容永遠是最新的，而在追蹤表
上做的標記不會污染原始項目。

### 比對範圍

- **同店**的 checklist 項目**與**筆記內文（有些事寫在本文、不在項目裡）。
- **全歷史**，不限日期。
- 跨店不撈（super_admin 也一樣依所在店別，與現有 `_scope_notes` 一致）。

### 增量比對：為什麼非做不可

`Note.content`、`Note.title`、`ChecklistItem.text` 都是 `EncryptedText`，**資料庫裡
是密文，SQL 無法比對**。現有搜尋的做法是把資料全撈出來、在 Python 端解密後比對
（`notes/routes.py:84` 的 `_PyPagination`，註解明寫「加密後無法 SQL ilike」），
而它前面有**日期範圍**（`_date_filter`）擋著，掃描量有上限。

本功能要全歷史，那道保護就沒了。以一店一天 100 個項目估，一年 3.6 萬筆 ——
每開一次頁面就要解密全部，一兩年後會明顯拖慢。

因此採**增量比對**：

- 每張追蹤表記一個**水位**（已掃到的位置）。
- 第一次建檔跑完整掃描（一次性的慢）。
- 之後只掃水位之後新增／異動的資料，命中就寫入。
- 開啟頁面時讀的是已存的命中列，是一般的索引查詢，永遠快。

### 資料模型

**`TrackedKeyword`** —— 一張追蹤表

| 欄位 | 說明 |
|---|---|
| `id` | |
| `store` | 所屬店別 |
| `keyword` | 追蹤的關鍵字。`EncryptedText`（可能是員工姓名，屬個資） |
| `created_by` / `created_by_name` / `created_at` | 誰建的 |
| `scanned_through` | 增量水位（見下方「水位的語意」） |

**`TrackedKeywordHit`** —— 一筆命中

| 欄位 | 說明 |
|---|---|
| `keyword_id` | FK → TrackedKeyword, CASCADE |
| `target_type` | `'note'` / `'item'` |
| `target_id` | 對應的 note_id 或 item_id |
| `note_text` | 備註，`EncryptedText`，nullable |
| `excluded_at` / `excluded_by` / `excluded_by_name` | 「不相關」的剔除紀錄，nullable |
| `matched_at` | 何時比對到的 |

唯一約束：`(keyword_id, target_type, target_id)` —— 同一筆資料不重複命中。

**軟刪除的處理**：`Note` 與 `ChecklistItem` 都有 `deleted_at`（軟刪除，24 小時後才
真的清掉）。比對時跳過已軟刪的資料；顯示時也要即時過濾 —— 因為一筆資料可能是先被
比對到、之後才被刪。已存在的命中列**不主動清除**（原始資料可能只是暫時被刪、24 小時
內可還原），改為顯示時過濾。原始資料被硬刪之後，命中列會因為 join 不到而自然消失。

**剔除用軟刪除而非真刪**：真刪的話下一輪增量比對會再把它抓回來（它仍然含有關鍵字）。
`excluded_at` 有值就代表「已判定不相關」，比對時跳過、頁面上不顯示。

### 水位的語意

水位不能只用「最大 id」，因為**既有項目的文字被編輯後也可能開始命中**。
採兩段判定：

- `scanned_through` 存**時間戳**（上次掃描完成的時刻）。
- 增量掃描的條件是 `updated_at > scanned_through`（涵蓋新增與異動，兩者都會 bump
  `updated_at`）。

⚠️ **注意與需求一的交互作用**：需求一刻意讓掛標籤**不**碰 `updated_at`。這是對的
（不能因為掛標籤就改變排序），而掛標籤也不會改變文字內容、不影響關鍵字比對，
所以兩者沒有衝突。但**日後若有人讓某個操作停止更新 `updated_at`，就會在這裡造成
漏掃** —— 需在程式與測試中標註這層依賴。

### 比對邏輯抽成獨立函式

比對本身（給定關鍵字與一批資料，回傳命中）要抽成一個純函式，與「從哪裡取資料」
解耦。原因：完整掃描與增量掃描是同一套規則，只是輸入不同；抽開之後兩條路徑不會
漂移，也方便單獨測試（大小寫、空白、部分比對等）。

比對規則：**不分大小寫的子字串比對**，與現有搜尋一致（`notes/routes.py:469`
的 `keyword.lower()`）。不做分詞、不做模糊比對 —— 使用者已接受「只是順口提到也會
被抓進來」，那正是「不相關」按鈕存在的理由。

### 權限

- 建立／刪除追蹤表：**同店的人都可以**，與現有標籤管理一致，不新增權限概念。
- 剔除與備註：同上，整店共用。

## 實作順序

兩個需求**彼此獨立**，沒有共用的資料或程式路徑，建議拆成兩個階段分別實作與部署：

1. **先做需求一（快速標籤鍵）**——範圍小、每天都在痛、且不需要新資料表（只加三個
   欄位）。可以先讓交接的體力活立刻減輕。
2. **再做需求二（建檔追蹤）**——需要兩張新表、增量比對、新頁面，範圍大得多。

分階段的另一個理由：需求一附帶修正的「標籤全刪重插」缺陷會動到既有的標籤儲存路徑，
值得單獨部署觀察，不要和大功能混在一起上線。

## 測試策略

### 需求一

- 按快速鍵掛上標籤後，`item.updated_at` **不變**（硬性條件，回歸防護）。
- 再按一次會移除。
- `tagged_by` / `tagged_at` 有被記錄。
- **從標籤選擇器改動其他標籤後，原有標籤的 `tagged_by` / `tagged_at` 仍在**
  （守住差集改寫，這是最容易回歸的一條）。
- 已有 5 個標籤時按快速鍵 → 回明確錯誤。

### 需求二

- 比對函式的單元測試：大小寫、部分比對、無命中。
- 建檔後跑完整掃描，命中數正確。
- 新增一個含關鍵字的項目 → 增量掃描抓得到，且**不重複**既有命中。
- 編輯既有項目使其開始含關鍵字 → 增量掃描抓得到（水位用 `updated_at` 的理由）。
- 剔除後：頁面不顯示，且**下一輪增量掃描不會把它抓回來**。
- 備註可寫入、可修改。
- 跨店資料不會出現在別店的追蹤表裡。

## 明確不做（YAGNI）

- **不做分詞或模糊比對**——子字串比對加上「不相關」按鈕已足夠。
- **不做每人各自的剔除清單**——使用者選擇整店共用。
- **不把追蹤表做成真的筆記**——會把日報洗版，且複本會與原始資料脫節。
- **不做跨店追蹤**——與現有的店別隔離一致。
- **不做「有備註的浮到最上面」**——使用者確認只要備註顯示在每一列的最上面。
- **需求一不新增 `quick` 欄位**——沿用釘選。
