# 建檔追蹤 — 本機測試腳本

> 目的：在推上 prod 之前，用本機假資料把功能走一遍。
> 種子資料的命中數是**用真的掃描程式碼實測過的**，數字對不上就是有問題，請回報。

## 0. 準備（兩行）

```bash
cd ~/project/webapp/app_unified
bash scripts/run_local.sh          # 另開一個終端機讓它一直跑
```

再開一個終端機，灌入建檔追蹤的測試資料：

```bash
cd ~/project/webapp/app_unified
set -a; source .env.local; set +a
../venv/bin/python scripts/seed_tracking_demo.py
```

> 這支腳本是 idempotent 的，重跑不會產生重複資料。
> 想清掉重來：`../venv/bin/python scripts/seed_tracking_demo.py --reset`

登入：<http://localhost:5000/dev> —— 免密碼，點名字就切換身分。

| 帳號 | 角色 | 店別 |
|---|---|---|
| `alice` / `bob` | user | 北店 |
| `carol` / `dave` | user | 南店 |
| `admin_north` | admin | 北店 |
| `admin` | super_admin | 北店 |
| `super_admin` | super_admin | **無店別** |

## 種下的資料與**實測**命中數

| 關鍵字 | 店別 | 應該找到 |
|---|---|---|
| `Kevin` | 北店 | **15 筆**（5 筆標題 + 5 筆內文 + 5 個項目）|
| `陳美玲` | 北店 | **3 筆** |
| `Kevin` | 南店 | **2 筆** |

另外種了但**不該出現**的：1 篇已軟刪的筆記、1 個已軟刪的項目、1 篇 AI 摘要——三者都含 `Kevin`。

## 一、基本流程（用 `alice`，北店）

1. 進 `/notes/`，toolbar 應該看得到 **🔎 建檔追蹤**。點進去 → 空清單，顯示引導文字。
2. 回 `/notes/`，展開「⚙️ 進階篩選」，搜尋 `Kevin`。
3. 結果上方出現 **「Kevin」＋ 建檔追蹤按鈕**。按下去。
   - 按鈕應變成 **建立中…**（第一次是全歷史掃描）。
4. 跳到追蹤表 → **應該有 15 列**。標題是「Kevin 建檔追蹤」。
5. 標題附近應該有 **最後更新：MM/DD HH:MM**（會比現在早幾秒，這是對的——它顯示的是資料實際被檢查過的時間）。
6. 列的順序是**新到舊**；每一列最上面是備註輸入框，下面才是日期／來源／原文。

## 二、備註（這是最重要的欄位）

7. 在某一列的備註框打字 → **點別的地方讓它失焦** → 重整頁面 → 文字還在。
8. 備註存好之後，那一列應該顯示 **誰在什麼時候改的**。
9. 再改一次同一則備註 → 顯示的人與時間要更新。
10. 把備註**清空** → 重整 → 確實是空的。
    （清空這個動作有被記進 log，舊文字在資料庫裡留著，只是目前沒有畫面可以看。）
11. 貼一段**超過 500 字**的文字 → 輸入框本身就會擋住，不會讓你打進去。

## 三、不相關（整店共用、可復原）

12. 對某一列按 **[不相關]** → 按鈕變成「再按一次確認」→ **不要按第二次**，等 4 秒 → 應該自己變回「不相關」。
13. 這次按兩下 → 該列消失。重整 → 仍然不在。
14. 頁面下方應該有 **「已剔除 (1)」** 的摺疊區 → 展開 → 看得到剛剛那筆，含**誰剔除的、什麼時候**。
15. 按它的**復原** → 該列回到主清單。重整確認。
16. 換 `bob`（同樣北店）登入 → 開同一張追蹤表 → **看到的剔除狀態跟 alice 一樣**（整店共用，不是每人一份）。

## 四、增量掃描（這是這個功能的核心）

17. 新增一則含 `Kevin` 的 checklist 項目 → 回追蹤表 → **新項目有出現**，且原本的 15 筆沒有變成 30 筆。
18. 找一個**原本不含** `Kevin` 的既有項目，把它**編輯成**含 `Kevin` → 回追蹤表 → 它出現了。
    （這條在驗水位是用 `updated_at` 而不是「最大 id」——只看 id 的話編輯過的舊資料永遠抓不到。）
19. 把步驟 13 剔除掉的那筆，去把它的**原文編輯一下**（隨便改個字）→ 回追蹤表 → **它不可以復活**。
20. **刪除**一則含 `Kevin` 的筆記 → 回追蹤表 → 該列消失。
21. 到 `/admin/` 把它**還原** → 回追蹤表 → **它要回來**。
    （這條是全分支審查抓到的 Critical：還原時如果沒有更新 `updated_at`，這筆資料就永遠掃不到了。）

## 五、店別隔離

22. 回 `/notes/` 搜尋 `Kevin` → 上方按鈕應該變成 **開啟追蹤表**（不是再建一張）。
23. 換 `carol`（南店）登入 → 搜尋 `Kevin` → 建檔追蹤 → **只有 2 筆**（南店的），看不到北店那 15 筆。
24. `carol` 的 `/notes/tracking/` 清單裡**看不到**北店那張表。

## 六、super_admin 的店別範圍（容易出錯的一段）

25. 用 `admin`（super_admin，北店）登入，**不要**指定店別，搜尋 `Kevin`。
    → 結果橫跨兩店，所以**不該出現建立按鈕**，應該顯示「請先在上方選一間店別」。
26. 點上方店別頁籤切到 **南店**，再搜尋 `Kevin` → 這時才有建立按鈕。按下去。
    → 建出來的表要是**南店**的（2 筆），不是 admin 自己的北店。
27. 在那張南店表上：點得進去、備註存得起來、刪得掉（不會 403）。
28. 用 `super_admin`（**無店別**）登入 → 進 `/notes/tracking/` → 應該看到明確的「找不到店別」錯誤，
    **不是**一個空清單。（空清單會讓人以為「這店沒東西」，而不是「你沒有店別」。）

## 七、順便驗一下這次一起修的東西

29. 進階篩選面板：**收起來** → 重整 → 應該還是收著的。
    再切一次排序（讓網址帶上 `?sort=created`）→ 重整 → **仍然收著**。
    （這就是你回報的那個 bug：以前只要 URL 上有任何篩選條件，就會強制展開、蓋掉你的選擇。）
