# 建檔追蹤 — 上線後人工測試

## 前置
- 用**有 notes 權限、非種子 admin** 的帳號登入（種子 admin 會 bypass 權限，驗不到模組開關）。
- 記下自己的店別；本功能完全綁店別。
- **位址列看到的路徑跟本文不一樣是正常的**：站台有全站的路徑別名（`app.py`
  的 `PATH_ALIAS`），`/notes/...` 一律會被改寫成 `/n/...` 才出現在瀏覽器
  網址列 / 連結上（例如本文寫的 `/notes/tracking/` 實際會看到
  `/n/tracking/`）。這是刻意設計（避免 Chrome 網址列/autocomplete 看出功能），
  **不是 bug**，回報問題時請認得出來，不要誤報「路徑變短了」。

## 步驟
1. `/notes/` toolbar 有「🔎 建檔追蹤」→ 點進去，空清單應顯示引導文字。
2. 回 `/notes/`，搜尋一個確定有多筆命中的關鍵字（例如某位同仁的名字）。
3. 結果上方出現「建檔追蹤」→ 按下。**第一次會跑完整掃描，可能等幾秒**，按鈕會變「建立中…」。
4. 跳轉到追蹤表，確認命中筆數與搜尋結果數量相當（不必完全相同：搜尋是以「筆記」為單位，
   追蹤表是以「筆記／項目」為單位，同一篇筆記裡兩個命中項目會是兩列）。
5. 頁面最上面有一個備註框（整張表共用一欄，不是每一列各自一個）→ 打字 →
   點別處 → 重整 → 備註仍在，且還在頁面最上面。
6. 對一列按「不相關」→ 消失 → 重整仍不在。
7. 回筆記新增一個含該關鍵字的 checklist 項目 → 重開追蹤表 → 新項目出現。
8. **修改**一個原本不含關鍵字的既有項目，讓它含關鍵字 → 重開追蹤表 → 該項目出現
   （這條驗的是水位用 updated_at 而非最大 id）。
9. 把步驟 6 剔除的那一筆原始資料編輯一下（隨便改個字）→ 重開追蹤表 →
   **它不可以復活**。
10. 回 `/notes/` 再搜尋同一個關鍵字 → 上方按鈕應變成「開啟追蹤表」。
11. 用**別間店**的帳號登入 → `/notes/tracking/` 看不到這張表；直接打
    `/notes/tracking/<id>` 應回 403。
12. **建立失敗的路徑**（自動化測試碰不到、只有人工能驗）：用瀏覽器 devtools
    的 Network 面板把 `/n/api/tracking`（實際路徑，見前置的路徑別名說明）設成
    離線 / 擋掉，回到有「建檔追蹤」按鈕的搜尋結果頁再按一次 → 按鈕應該變成
    看得見的失敗訊息（例如「建立失敗，再試一次」），而不是停在「建立中…」看
    起來像沒反應；幾秒後文字要恢復成「建檔追蹤」可以再按。取消攔截後再按一次
    應該能正常建立成功。
13. **super_admin 的店別範圍**（需要一個 super_admin 帳號才能驗，一般帳號沒有
    `?store=` 可切）：用 super_admin 登入，**不要**在網址帶 `?store=`，直接搜尋
    一個只有某一店有命中的關鍵字 → 結果上方**不應該出現「建檔追蹤」按鈕**，
    應該看到提示文字要求先選一間店。接著用上方的店別分頁切到有命中的那一店
    （網址會帶 `?store=`）再搜一次同一個關鍵字 → 這次應該出現「建檔追蹤」，
    按下後到追蹤表列表頁（同樣帶著這個 `?store=`）確認新表確實出現在**這一
    店**、不是 super_admin 自己登入帳號預設的那一店。

## 效能觀察（只在 prod 看得到）
- 步驟 3 的完整掃描期間，另開一個分頁操作其他頁面應**不會卡住** ——
  掃描是分批解密、批間 `gevent.sleep(0)` 讓出 hub。若明顯卡住，
  到 monitor service 看有沒有 `hub_block` 事件，並回報。
